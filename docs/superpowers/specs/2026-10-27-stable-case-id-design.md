# Стабильный id дела: одна формула везде, слияние дублей, безопасная переиндексация

Эпик: `courts-271g` (beads в courts). Замеры: memory `project_case_id_formula_drift`.

## Зачем

`_id` дела в `sudata` — `{court}_{YYYY-MM-DD}_{номер}`, номер извлекает
`build_case_id` из строки номера. Формула менялась (27.04 — тильда, 02.10 —
кассационные скобки), номер карточки на sudrf со временем меняется
(перерегистрация в новом году, появление производства в скобках), а суд правит
дату регистрации задним числом. Отсюда дубли: одно дело (один `case_uid`) лежит
под двумя `_id`. Пример: `78OS0000_2008-12-09_2-2` (старое скачивание) и
`78OS0000_2008-12-09_2-1` (WARC 2026-06-19), номер `2-1/2011 (2-2/2010;)`,
один `uuid`.

Индекс должен уметь пересоздаваться с нуля, поэтому «первый увиденный id» как
ключ не годится — id обязан быть **детерминированной функцией данных**, не
зависящей от порядка индексации. Сам `uuid` ключом быть не может: его нет у
~76 млн из 218 млн документов (МГС и старые карточки sudrf с пустым `_uid=`), а
адреса существующих дел пришлось бы менять все. Поэтому: формула от номера,
даты и суда для каждой записи + детерминированное правило выбора, когда
несколько записей с одним `uuid` дают разные id.

## Цели

1. Новые дубли не возникают: все скачивания одной карточки сходятся в один
   документ — по формуле, а для карточек с `uuid` ещё и по правилу группы.
   Итоговый id не зависит от порядка прихода записей (пересборка индекса с
   нуля даёт те же id).
2. Существующие дубли слиты в один документ без потери скачиваний/документов.
3. Переиндексация старых JSONL (записи со старым `id_final`) ложится на те же
   id, что и свежие скачивания.
4. Формула одна и та же во всех местах, где вычисляется id (courts и index).

## Не цели

- МГС (`77*`, `parse_html_mgs.card_case_id` / `mgs_downloader.dump.custom_id`)
  не трогаем: там свой осознанный ключ (номер дела до `~`, дата второй строки
  «Истории состояний»), id МГС с формулой sudrf не пересекаются.
- Редиректы со старых адресов sud.report не делаем — смена адреса у
  перенесённых дел допустима; пользовательские «Блокноты»/«Сохранённые»,
  ссылающиеся на старые id, не переносим — потеря допустима (решения
  пользователя).
- Схему ES не меняем (memory `project_es_schema_fixed`).

## Анти-цели

- Мусорные id (`4У-48-2017 - (4У-2189`, `_Материалы дел`) — хуже дубля.
- Слияние разных дел. Сливаем только при совпадении формульного id или `uuid`;
  по похожести номеров — никогда (memory `project_case_id_complaint_key`).
- Обнуление полей при неудачном исправлении (memory `feedback_no_null_index_fields`).

## Правило: ключ — первый выданный номер карточки

Решение пользователя: id строится по номеру, который карточка получила первой.
Правило по веткам (сверху вниз, первая подходящая):

| # | Случай | Ключ | Пример → номер в id |
|---|--------|------|--------------------|
| 0 | Пустой `date_reg` | id нет (`None`), как сейчас | |
| 1 | Заглушка `…-0/… [X/YYYY]` | производство в скобках; при 01.01.1900 — год производства (как сейчас) | `4У-0/2011 [44У-113/2011]`, 01.01.1900 → `2011-01-01_44У-113` |
| 2 | Тильда, после `~` есть номер с годом | часть после `~` (номер материала) | `2-408/2026 ~ М-196/2026` → `М-196` |
| 3 | Тильда, после `~` номера нет | часть до `~`, дальше по правилам 4–6 | `2-1043/2009 ~ Материалы дела` → `2-1043` |
| 4 | Кассация `A [B]` | ключ из головы `A` (жалоба), голова разбирается правилами 5–6 | `8Г-4094/2022 [88-5730/2022]` → `8Г-4094`; `4У-48/2017 - (4У-2189/2016) [44У-19/2017]`, рег. 2016 → `4У-2189` |
| 5 | Несколько номеров, год регистрации среди них есть | последний номер с годом регистрации (как сейчас) | `4У-47/2017 - (4У-2186/2016)`, рег. 2016 → `4У-2186`; `33-83/2012 (33-19377/2011;)`, рег. 2012 → `33-83` |
| 6 | Несколько номеров, года регистрации нет | номер с самым ранним годом (при равенстве — последний в строке) | `2-1/2011 (2-2/2010;)`, рег. 2008 → `2-2`; `2-1/2012 (2-3/2011; 2-12/2010;)` → `2-12` |
| 7 | Один номер | номер до последнего `/` (как сейчас) | `2-5/2020` → `2-5` |

Номер в id: `/` → `-` (как сейчас). Результат никогда не содержит пробелов,
`(`, `[`, `~`; если правило не нашло номер — `…_ID_NOT_PARSED` (как сейчас).

Дата в id — `date_reg` записи, как сейчас. Альтернативу — дату события
«Регистрация…» из «Движения дела» — рассмотрели и отклонили: см. «Факты о данных».

Чего правило не закроет: карточка теряет самый ранний номер (в 2011 году наше
дело уже не показывало номер 2008 года), а суд правит дату регистрации. Формула
от одной записи здесь стабильной быть не может — неизменен только `uuid`.
Поэтому для карточек с `uuid` id — функция **всех** скачиваний карточки
(решение пользователя):

**Правило группы.** Документы с одним `uuid` — одно дело. Для каждого считаем
формульный id; побеждает id с **самой ранней датой**; при равной дате — формула
от самой свежей записи (по `version_ts`, она несёт самый полный номер); при
полном равенстве — лексикографически меньший id. Выбор не зависит от порядка
прихода записей, поэтому пересборка индекса из того же набора данных даёт те же
id. Если позже придёт скачивание с ещё более ранней датой, группа переезжает на
него (так и должно быть: окончательное состояние детерминировано).

Без `uuid` (МГС и старые карточки sudrf с пустым `_uid=`, ~35% индекса) — только
формула; правки даты судом там не ловятся.

Ожидаемый перенос существующих документов (оценки по случайным выборкам
сентября–октября 2026, с запасом):

| Случай | Документов не на формульном id |
|--------|-------------------------------|
| Кассация `[...]` (ключ производства вместо жалобы) | ~1,5 млн из 2,17 млн; ~165 тыс. уже имеют близнеца |
| Тильда, старый id «до `~`» | ~0,16 млн, почти все с близнецом |
| Тильда без номера после `~` | ~0,3 млн, близнецов нет (сейчас id верный, ломается только при переиндексации) |
| Правило 6 | ~5–10 тыс. |

## Факты о данных (проверено на `sudata`)

- `uuid` — это `case_uid` **карточки**, а не производства: жалобы одного
  производства — разные карточки с разными `uuid`; один `uuid` = одна карточка
  (memory `project_case_id_complaint_key`, сверено по `downloaded_cases`).
  Поэтому слияние по равному `uuid` не склеивает разные дела.
- Всё нужное для пересчёта есть в doc values, `_source` не нужен:
  `case_number` — keyword с исходной строкой (`[`, `~`, `;` на месте);
  `date_reg` — date, `docvalue_fields` с `format: yyyy-MM-dd` даёт
  `1900-01-01` для заглушки; `court_code` == `court_id`; `uuid` — keyword.
  Скан через `docvalue_fields` идёт ~1–3 тыс. док/с на весь индекс; с фильтром
  `regexp` по `case_number` быстрее (так делались замеры).
- `date_reg` у одной карточки между скачиваниями **не стабилен**. Выборка
  10 тыс. документов с `uuid`: у 1,64% `uuid` больше одного `_id`, в 140 из 164
  групп различается дата (61 — на 1 день, 65 — на 2–7 дней, 14 — больше), в 24 —
  только номер. Суд правит дату в карточке задним числом: событие «Регистрация…»
  в «Движении дела» внутри групп-дублей различается в 12 из 39 случаев
  (`01.06` → `09.06`, «Регистрация иска» → «…и принятие его к производству»).
  Дата события «Регистрация…» как источник не годится: где оно есть, оно на 99,5%
  уже равно дате в id, а у ~60% документов его нет (нет «Движения дела» или
  первое событие — «Передача дела судье»).
- Вероятный источник части дат-дублей — courts `watch.py`: `load_case_by_uid`
  ищет по `(court_id, date_reg, uid)`, а дата из карточки («Дата поступления»)
  может отличаться от даты в выдаче поиска → запись не находится → новый id.
  Гипотеза, средняя уверенность.
- Близнец на формульном id с **другим** `uuid` редок: 2 из 500 (тильда),
  1 из 8 868 (кассация).
- По `_id` в index ключуется ещё конверт `hidden_since` из открытых данных МГС —
  МГС вне области, не затронут.

## Компоненты

### 1. Формула — одна, две копии, общий эталон

- courts `src/courts/parser/search_result_parser.py:build_case_id` — источник
  истины; index `src/utils/case_id.py` — побайтовая копия (как сейчас).
- Эталонный набор `case_id_golden.json` — список
  `{case_number, date_reg, court_id, expected}` со всеми примерами из таблицы
  выше и реальными номерами из выборок (включая уже верные, чтобы зафиксировать,
  что они не сдвинулись). Файл лежит в обоих репо, содержимое идентично; тест в
  каждом репо прогоняет `build_case_id` по нему.
- Все вызывающие в courts (`downloader/watch.py`, `scripts/backfill.py`,
  `scripts/backfill_downloaded_cases.py`, `scripts/fix_case_ids.py`) берут
  функцию из `search_result_parser` — проверить, что импорт именно оттуда.
- index-worktree'ы (`index-prio`, `index-opendata`, `indexed-at`) получают
  формулу через main, отдельной работы не требуют.

### 2. Пересчёт id для любого источника (index)

`to_document` пересчитывает id из полей записи, а не берёт сохранённый:
`court_id` или `court_code`; `date_reg` в `дд.мм.гггг` или `гггг-мм-дд`
(в т.ч. с `T00:00:00Z`). Сохранённый `ID`/`id_final` — только если пересчёт
невозможен (нет номера/даты). `main._derive_id_final` (JSONL) перестаёт
доверять `id_final` из записи по той же причине. Сейчас на JSONL
(`court_code` + ISO-дата) пересчёт молча падает и используется старый
`id_final` — это и есть дыра цели 3.

### 3. Слияние по `uuid` при индексации (index)

Перед записью пачки `BulkIndexer` ищет в ES документы с теми же `uuid`, но
другим `_id` (`terms` по `uuid`, исключая МГС и документы без `uuid`). По
правилу группы выбирается целевой id (входящая запись тоже кандидат); остальные
документы группы вливаются в целевой (`merge_docs`, как в
`dedup_bracket_ids --fold`) и удаляются в том же `_bulk`. Ошибка поиска валит
пачку (как сделано для `mget` в `6f45dfb`), а не пишет без проверки.

### 4. Миграция существующего индекса (index, скрипт)

Скрипт в стиле `scripts/dedup_bracket_ids.py`, пользователь запускает сам:

1. **Выгрузка**: скан `sudata` (`docvalue_fields`, без `_source`) — `_id`,
   `case_number`, `date_reg`, `court_code`, `uuid`; на выходе jsonl
   документов, где `_id` ≠ формула. МГС пропускаются.
2. **Проверка** (без записи): по каждому — есть ли близнец на формульном id,
   совпадает ли `uuid` у пары; сводка по случаям.
3. **Перенос**: нет близнеца — документ переписывается на формульный id; есть
   близнец с тем же `uuid` (или у обоих `uuid` нет) — вливается через
   `merge_docs`; близнец с другим `uuid` — не трогаем, в отдельный файл на
   ручной разбор.
4. **Удаление** старого `_id` только после подтверждённой записи нового.
5. **Слияние по `uuid`**: группы с одним `uuid` и несколькими `_id` после шагов
   1–4 сливаются в документ, выбранный правилом группы (самая ранняя дата).
   Масштаб по выборке: порядка 1–2 млн лишних документов (оценка грубая —
   выборка документов, а не `uuid`, завышает крупные группы).

Батчи, резюмируемость по файлу, идемпотентность повторного запуска — как в
`dedup_bracket_ids`.

### 5. courts: очередь и `downloaded_cases`

`downloaded_cases` ключуется `(case_id, hashed_id)`, поиск отсеивает уже
скачанное по `hashed_id = blake2s(case_id)`. После смены формулы карточки
изменённых случаев получат новый `hashed_id` и уйдут на повторное скачивание.
Для этого уже есть колонки `case_id_new`/`hashed_id_new` и
`scripts/backfill_downloaded_cases.py`.

В courts id нужен только для очереди и манифеста; окончательный `_id` в ES
выбирает index (формула + правило группы). Поэтому courts применяет одну
формулу и не обязан знать правило группы. `watch.py` ищет уже скачанную
карточку по `(court_id, uid)` — без `date_reg`, иначе правка даты судом
порождает новую запись (`database.CASE_BY_UID_SQL`, `load_case_by_uid`).

## Порядок раскатки

1. Формула + эталон в courts и index (одним изменением по смыслу), тесты.
2. index: пересчёт id в `to_document`/`_derive_id_final`; слияние по `uuid`.
3. courts: обновление `downloaded_cases` (`case_id_new`/`hashed_id_new`) до
   деплоя новой формулы в поисковик, иначе волна повторных скачиваний.
4. Миграция `sudata` скриптом (пользователь).
5. Контроль: повторная выборка как в замерах — доля `_id ≠ формула` ≈ 0,
   групп с одним `uuid` ≈ 0.

## Оставлено исполнителю

- Точная регулярка разбора пар «номер/год» (должна проходить эталон, включая
  `Вх. № -2098/2010`, `2а-2/21/2025`, `4/17-578/2013`).
- Структура скрипта миграции и CLI — по образцу `dedup_bracket_ids.py`.
- Где именно в `BulkIndexer` делать поиск по `uuid` (вместе с существующим `mget`).

## Решения, принятые за пользователя (проверить)

- МГС вне области изменений.
- Правило 5 оставляем «последний номер с годом регистрации», а не «самый ранний
  год»: иначе сдвигаются ~0,7% стабильных id вида `33-83/2012 (33-19377/2011;)`.
- Правило 3: если после `~` нет номера — ключ по части до `~` (так эти дела
  уже лежат в индексе, перенос не нужен).
- Близнец с другим `uuid` не сливается автоматически, уходит на ручной разбор.
- В правиле группы при равной дате — формула от самой свежей записи, затем
  лексикографический минимум; в `merge_docs` свежая запись идёт входящей (как
  `fold` в `dedup_bracket_ids`).
- courts `watch.py` ищет скачанную карточку по `(court_id, uid)` без даты;
  courts не знает правила группы, им владеет index.
- Миграция идёт при работающем индексере: удаление старого `_id` и перезапись —
  с `if_seq_no`/`if_primary_term`, конфликт = пропуск и повтор на следующем
  проходе.
- `downloaded_cases` переключается на новые id через `case_id_new`/`hashed_id_new`
  до деплоя формулы — повторных скачиваний нет; несколько старых строк,
  сходящихся в один новый id, допустимы (PK `(case_id, hashed_id)` не нарушается).
- Поиск по `uuid` в `BulkIndexer` — один `terms`-запрос на пачку; бюджет —
  не медленнее существующего `mget`, замерить на тестовом прогоне.
- Эталон берётся из реальных номеров выгрузки замеров (сохранить выборку в
  `tests/` при реализации) плюс примеры из таблицы.
